# SnapScale 🚀

A serverless image-processing platform built on AWS using Python (Pillow), AWS Lambda, S3, SQS, DynamoDB, API Gateway, and CloudFront. Developed as a resume project to explore cloud-native architectures, asynchronous event-driven pipelines, and production monitoring.

## Architecture & Data Flow

1. **Upload**: Clients upload original images up to 10 MB directly to an S3 bucket (`originals/`) using presigned POST URLs generated by an API Gateway + Lambda endpoint.
2. **Queueing**: S3 event notifications trigger an SQS queue (`snapscale-processing`) with a 180-second visibility timeout, max 3 receives, and a Dead Letter Queue (DLQ) for poisoned payloads.
3. **Processing**: An AWS Lambda processor (`Python 3.13`, 1024 MB RAM, 30 s timeout) polls SQS, downloads the original, and uses **Pillow** to generate three variants (**thumbnail**: max 150 px, **medium**: max 800 px, **large**: max 1600 px) while stripping EXIF metadata, preserving format, and never upscaling.
4. **Storage & Tracking**: Processed variants are saved to a private S3 bucket (`processed/<imageId>/...`) protected by CloudFront via Origin Access Control (OAC). Job statuses (`PENDING`, `PROCESSING`, `RETRYING`, `COMPLETED`, `FAILED`) and metadata are tracked in **DynamoDB** (`SnapScaleImages`).
5. **Monitoring & Alerts**: Integrated with Amazon SNS and CloudWatch alarms (tracking processing failures, DLQ messages, Lambda errors, and queue backlog) with a 14-day log retention policy.

---

## Tech Stack & AWS Services

* **Compute**: AWS Lambda (Python 3.13)
* **Storage**: Amazon S3 (Originals & Processed buckets with strict security policies)
* **Messaging**: Amazon SQS + DLQ, Amazon SNS
* **Database**: Amazon DynamoDB
* **API & CDN**: Amazon API Gateway (API Key auth, rate-limited) + Amazon CloudFront (OAC)
* **Infrastructure as Code**: AWS SAM (Serverless Application Model)
* **Monitoring**: Amazon CloudWatch (Dashboards & Alarms)

## Deployment & Execution Guide

### Prerequisites

* AWS CLI and AWS SAM CLI configured with an IAM deployer user (`snapscale-deployer`).
* Python 3.13 and virtual environment (`.venv`).

### 1. Build & Deploy Infrastructure

```powershell
# Build Lambda layers and package zip files
python build_lambda.py

# Deploy stack via AWS SAM CLI
sam deploy --guided

```

### 2. Testing & Running the Pipeline

```powershell
# Upload and process individual test images
python client.py

# Execute high-concurrency burst tests
python burst.py

# Analyze DynamoDB execution metrics (Read-Only)
python analyze_metrics.py

```

## Test Results & Metrics Summary

Testing was performed on **223 total records** in the system across various test cases (valid JPEGs/PNGs, corrupted files, oversized images, exceptions, and bursts).

* **Success Rate**:
* **Option A (Strict - all records that received a file)**: `97.74%` (216 / 221 records).
* **Option B (Headline - valid images only)**: `100.00%` (216 / 216 records). Excluded deliberate failure test cases (`test-bad`, `toowide.png`, `fake.txt`, `corrupt.jpg`, and two PENDING abandoned uploads).


* **Byte Reduction (Completed non-burst samples)**:
* **JPEG**: Thumbnail ~99.5%, Medium ~91.3%, Large ~73.5%.
* **PNG**: Thumbnail ~98.0%, Medium ~63.5%, Large ~2.0% (small sample size).


* **Server Latency (`completedAt - uploadedAt`, n=216)**:
* Average: `1.11 s` | Median: `1.01 s` | P95: `1.91 s` | Max: `8.37 s` (slow warm PNG case).
* Cold start initialization duration: ~600–990 ms. Max memory consumed: ~202 MB.


* **Burst Load Test Performance**:
* Tested with a burst of 100 concurrent image uploads.
* Peak queue depth remained at **0 messages visible / in flight** during the burst because client upload speed (~2 images/s) was slower than Lambda processing capacity.
* Official 100-image run completed successfully end-to-end in **46.6 seconds** with 100% success and 0 retries.

## Operational Monitoring & Alarms

CloudWatch monitoring is configured with 5 core alarms routed to an SNS topic (`snapscale-alerts`) sending email notifications:

* `snapscale-dlq-not-empty`: Triggers when messages land in the Dead Letter Queue.
* `snapscale-processing-failures`: Triggers on job failures.
* `snapscale-api-lambda-errors` & `snapscale-processor-lambda-errors`: Monitor function invocation errors.
* `snapscale-queue-backlog`: Monitors SQS message buildup.

*Sample Alert Event*: On 26 Oct 2026 at 08:04:51 UTC, `snapscale-dlq-not-empty` transitioned from `OK` to `ALARM` when a poisoned payload test routed a message to the DLQ.

---

## Limitations & Lessons Learned

* **Small Sample Size**: Metrics reflect a focused set of test images; byte reduction varies significantly based on source image resolution and compression.
* **Upload-Speed Bottleneck**: High-concurrency burst tests were limited by client-side upload speed rather than SQS/Lambda throttling.
* **No Up-scaling**: Variants are never upscaled beyond original dimensions; small images will yield lower compression savings on larger variant sizes.
* **Single Region**: Deployed exclusively in `ap-south-1` (Mumbai).
